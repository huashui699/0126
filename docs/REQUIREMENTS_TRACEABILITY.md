## 1. 状态定义

| 状态 | 定义 |
|---|---|
| 已上线 | 代码、数据、权限和生产部署均已验证 |
| 已完成 | 该阶段要求的交付物已完成并通过检查 |
| 已定义 | 需求/设计已写清，但尚未开发或尚未通过最终验收 |
| 进行中 | 已开始执行，仍缺少部分验收证据 |
| 未开始 | 尚未产生实现或阶段交付物 |
| 受阻 | 缺少授权、外部依赖或关键决策，无法继续 |

## 4. 已上线 V1 与目标 MVP 的边界

当前生产环境已上线的只有：

- 响应式新闻列表与新闻卡片。
- Supabase `news` 表匿名只读。
- 来源、时间、联赛、球队和中文摘要字段展示。
- 5 分钟页面重新验证和数据库失败预览兜底。

下列内容不得标记为“已完成”：球队选择、用户关注、登录同步、情报日历、来源自动采集、AI 翻译摘要、事件聚类、绿/蓝/红自动判定、状态历史、运营后台、通知和完整监控。

## 5. Day 2 对齐检查

| 检查项 | 原状态 | 处理结果 |
|---|---|---|
| 关注球队数量 | 项目计划下一迭代写 1–3，其他需求写 1–5 | 统一为 1–5 |
| 登录/注册优先级 | 总需求与 WBS 为 P0，页面表为 P1 | 页面表调整为 P0 |
| 运营后台优先级 | 总需求与 WBS 为 P0，页面表为 P1 | 页面表调整为 P0 |
| 日历范围 | P0 至少月历 + 手机日程；核心旅程另提周历 | MVP 验收以月历 + 日程为准，周历不阻断首期 |
| 红色传闻 | 总体 MVP 需要定义，最近闭环暂不自动接入低可信社区 | 保留 UI/数据规格；自动采集推迟到高质量来源闭环后 |

结论：Day 2 交付物与项目 P0 目标一致。发现的三个文档冲突已修正，没有新增超出 MVP 的功能，也没有把尚未实现的能力错误标记为完成。

## 6. 后续变更控制

每完成一个 Day，必须执行以下检查：

1. 将当日交付物映射到本矩阵中的需求 ID。
2. 只有同时具备实现、检查结果和可复核证据时，功能才能标为“已完成/已上线”。
3. 新需求必须标明 P0/P1/P2、依赖、验收标准和对 45 日排期的影响。
4. 发现文档冲突时，记录原状态、决策和修改结果。
5. 任何来源在 Day 3 审核通过前不得进入生产自动采集。
6. 每周 M0–M5 里程碑评审时复核未实现 P0、范围新增和延期风险。
