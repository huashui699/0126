## 1. 项目定义

### 1.1 一句话产品定位

0126 Football 是一款面向中国球迷的“球队订阅式情报日历”：用户选择自己喜欢的球队后，每天可以按日期查看来自官方渠道、新闻媒体、记者及合规社交平台的相关信息，并通过可解释的证据规则区分“官方确认、待核实、传闻/低可信”。

### 1.2 要解决的问题

球迷当前需要在球队官网、联赛官网、新闻网站、YouTube、X、微博等多个渠道之间反复切换，仍然难以快速判断：

- 今天与我支持的球队有关的重要信息有哪些？
- 信息最初来自哪里，是否能够追溯到原文？
- 这是官方消息、媒体报道，还是未经证实的传闻？
- 同一事件是否被多个独立来源证实？
- 某条消息后来是否被官方确认、否认或修正？

### 1.3 产品目标

1. 用户在首次使用的 1 分钟内完成球队选择并看到专属日历。
2. 每天自动聚合用户所关注球队的高价值信息，减少信息搜索成本。
3. 每条信息保留来源、原文链接、发布时间、采集时间和证据依据。
4. 通过规则与 AI 辅助分类，让用户快速识别信息状态，而不是让 AI 代替用户判断事实。
5. 建立可持续、合规、可扩展的信息采集与运营体系。

### 1.4 非目标（首期不做）

- 不做球迷社区、评论区和私信。
- 不做博彩、赔率推荐或比赛结果预测。
- 不全文转载受版权保护的文章，只展示必要标题、短摘要和原文链接。
- 不依赖违反平台条款的批量爬虫。
- 不宣称 AI 能证明新闻“绝对真实”。
- 不在首期覆盖所有球队、语言和社交平台。
- 不在当前 45 日 MVP 内开发 iOS、Android、鸿蒙或微信小程序，但架构必须保留这些客户端的接入能力。

## 2. 目标用户与核心场景

### 2.1 目标用户

- 核心球迷：每天关注 1–5 支球队，希望及时掌握转会、伤病、赛前和官方动态。
- 泛球迷：只想查看重要事件，不希望被大量重复消息淹没。
- 内容运营人员：维护球队、来源白名单、错误信息和可信度标签。

### 2.2 核心用户旅程

1. 用户进入产品，选择联赛和球队。
2. 系统创建关注列表，并默认打开“今天”的球队情报日历。
3. 用户从月历、周历或日程列表中查看当天信息。
4. 日历条目以状态文字、图标和颜色区分可信度。
5. 用户打开详情页，查看中文摘要、原文、来源身份、证据和更新时间。
6. 当信息被进一步证实或否认时，系统更新状态并保留变更记录。
7. 用户可选择接收每日摘要或重要官方消息提醒。

## 3. 信息范围与展示模型

### 3.1 信息类型

- 俱乐部公告：签约、续约、离队、管理层及商业公告。
- 比赛信息：赛程、比分、阵容、赛后报告。
- 球员动态：伤病、停赛、训练、国家队征召。
- 转会动态：报价、接触、谈判、体检、官宣。
- 教练与战术：发布会、训练信息、阵型变化。
- 官方社交动态：球队、球员、联赛和赛事组织方发布的内容。
- 可信媒体及记者报道。
- 社区热点与传闻：仅在来源合规且达到收录阈值时展示。

### 3.2 信息来源优先级

| 层级 | 来源 | 首期策略 | 可信度默认值 |
|---|---|---|---|
| P0 | 球队、联赛、足协、赛事组织方官网及认证账号 | 优先接入 | 高 |
| P1 | 具有编辑责任和稳定署名的主流体育媒体 | RSS、许可 API 或链接摘要 | 中高 |
| P2 | 球队及可信媒体的 YouTube 官方频道 | YouTube Data API | 中高 |
| P3 | 经过人工审核的记者、跟队记者和行业人士 | 平台 API + 来源白名单 | 中 |
| P4 | 论坛、社区、聚合账号和匿名爆料 | 后期、严格限流和人工复核 | 低 |

接入顺序建议：球队/联赛官网与 RSS → 主流媒体 RSS → YouTube → X 精选账号 → 其他社交平台。微博、抖音、微信公众号等渠道需要先确认开放接口、内容授权和商业使用条件，再决定自动化或人工录入方案。

### 3.3 日历模型

产品需要同时保留两个时间：

- `published_at`：信息首次发布的时间。
- `event_at`：信息所描述事件的发生或计划时间，例如比赛开球时间、发布会时间。

默认日历按 `published_at` 展示每日新情报；比赛与明确日程类内容按 `event_at` 展示，并注明“事件时间”。所有时间统一存储为 UTC，前端默认转换为 Asia/Shanghai。

日历提供：

- 月视图：查看每天的信息数量和不同状态分布。
- 周视图：查看未来赛程和近期球队动态。
- 日程视图：适合手机连续浏览。
- 筛选器：球队、信息类型、可信度状态、来源类型。
- 去重聚合：同一事件的多篇报道合并为一个“事件簇”，详情中列出全部来源。

## 4. 可信度与 AI 机制

### 4.1 标签定义

| 标签 | 颜色 | 含义 | 最低判定条件 |
|---|---|---|---|
| 官方确认 | 绿色 | 可追溯至球队、联赛、足协、赛事方或当事人的认证官方渠道 | 命中已审核官方来源，原文可访问，内容与主体直接相关 |
| 待核实 | 蓝色 | 有明确来源，但尚无官方确认，或只有一个可信非官方来源 | 来源已识别，未发现明显伪造或冲突，但证据不足以确认 |
| 传闻 / 低可信 | 红色 | 来源匿名、转述链过长、证据不足、历史准确率低，或被可靠来源反驳 | 触发低可信规则，必须清楚显示风险原因 |

颜色不能单独承担含义。界面必须同时显示文字标签和图标，例如“✓ 官方确认”“? 待核实”“! 传闻”，以兼顾色觉障碍和降低误读。

### 4.2 重要产品原则

- AI 输出的是“证据支持程度”，不是事实真伪的最终裁决。
- “官方来源”不等于内容永远正确，但可确认该主体确实作出了该表述。
- 可信度标签必须可以解释、复核、修正和追踪历史。
- AI 不得仅凭文风、情绪或账号粉丝数判定真伪。
- 涉及伤病、纪律、犯罪、隐私等敏感内容时，提高发布阈值并允许人工审核。

### 4.3 判定信号

每条信息或事件簇记录以下证据信号：

1. 来源身份：是否在官方/媒体/记者白名单中。
2. 原始性：是第一手发布、媒体采访，还是多层转述。
3. 独立佐证：是否有两个或更多相互独立的可靠来源。
4. 引用完整性：是否链接到原文，引用是否与原文一致。
5. 时间一致性：发布时间、事件时间和上下文是否合理。
6. 历史表现：来源过去被确认、否认或删除的比例。
7. 冲突检测：是否存在官方否认或可靠来源的相反报道。
8. 内容风险：是否存在明显标题党、伪造截图、无主体或无证据断言。

### 4.4 建议评分结构

系统内部可保留 0–100 的 `confidence_score`，但用户界面以标签和证据解释为主。

```text
基础来源分 + 第一手证据分 + 独立佐证分
- 匿名/转述惩罚 - 冲突惩罚 - 过期信息惩罚
```

标签不是简单固定分数映射：官方确认必须满足“官方来源验证”硬条件；即使普通媒体得分很高，在官方确认前仍应是蓝色。红色标签需要显示具体原因，不允许只显示“AI 认为不可信”。

### 4.5 标签状态流转

```text
新采集 → 待处理 → 蓝色（待核实）
                    ├─ 官方发布/确认 → 绿色（官方确认）
                    ├─ 多方佐证但未官宣 → 保持蓝色，提高证据等级
                    └─ 被否认/证据异常 → 红色（传闻/低可信）
```

所有状态变化写入审计记录：旧状态、新状态、变更原因、证据、模型版本、操作人和时间。

## 5. 功能需求

### 5.1 P0：MVP 必须具备

#### A. 球队目录与关注

- 按联赛浏览球队并支持搜索。
- 用户可以选择、取消和排序喜欢的球队。
- 未登录用户可本地保存；登录用户跨设备同步。
- 首期覆盖五大联赛的 14 支高关注球队，其中英超 6 支、其他四个联赛各 2 支；具体名单与来源见 [SOURCE_REGISTRY.md](./SOURCE_REGISTRY.md)，验证后再扩充。

#### B. 情报日历

- 月历、周历和日程列表至少先完成“月历 + 手机日程列表”。
- 每日显示信息总数及绿/蓝/红分布。
- 支持按球队、类型、可信度筛选。
- 点击条目进入信息详情。

#### C. 信息详情与来源追溯

- 中文标题和 AI 中文摘要。
- 原始标题、来源名称、作者、发布时间和原文链接。
- 可信度标签、评分更新时间和“为什么这样标记”。
- 同一事件的其他独立来源。
- 后续更正、否认或官宣的状态历史。

#### D. 信息采集与处理

- 定时拉取官方/RSS/API 数据。
- 标准化、语言识别、球队实体匹配、去重和事件聚类。
- AI 翻译、摘要、类型分类和证据信号提取。
- 失败重试、采集日志和来源健康检查。

#### E. 运营后台

- 管理球队、别名和官方账号。
- 管理来源白名单、黑名单和来源级别。
- 查看待复核信息及 AI 判定依据。
- 手动改标签、合并事件、隐藏内容并记录原因。

### 5.2 P1：MVP 验证后

- 邮件、站内或 Web Push 每日摘要。
- 只对“官方确认”或状态变化发送即时提醒。
- 用户自定义关键词、球员和信息类型。
- 来源关注与屏蔽。
- 中英文原文对照。
- 可信度变更通知与纠错反馈。

### 5.3 P2：增长阶段

- 更多联赛、国家队和女足。
- 多平台官方账号自动映射。
- 个性化排序和摘要长度偏好。
- 赛前/赛后专题时间线。
- 数据质量与来源准确率公开页。

## 6. 非功能需求

- 性能：移动端首屏主要内容在正常 4G 网络下 3 秒内可用。
- 可用性：采集任务失败不影响已入库内容浏览；核心数据每日任务成功率 ≥ 99%。
- 时效性：官方渠道目标 15 分钟内入库，普通 RSS 30 分钟内入库。
- 安全：密钥只保存在服务端；Supabase 启用 RLS；管理员操作需要审计。
- 隐私：只收集提供关注和通知所必需的数据，提供注销与数据删除入口。
- 版权：默认保存元数据、短摘要和原文 URL，不复制整篇文章或完整视频字幕。
- 合规：优先使用官方 API、RSS 或许可数据源，并遵守展示、缓存、删除和署名要求。
- 可解释性：所有可信度标签均可展示至少一项机器可读的判定理由。
- 可扩展性：核心数据、认证、可信度、关注、日历和通知能力通过平台无关领域服务与版本化 API 提供，不绑定 Web 页面实现。

## 7. 技术方案

### 7.1 当前基础

- 前端：Next.js 16.3、React 19、TypeScript、Tailwind CSS。
- 数据：Supabase Postgres，当前已有只读新闻展示。
- 部署：GitHub + Vercel 自动部署。
- 已上线能力：首页、新闻卡片、来源/时间/摘要展示、Supabase 数据读取。

### 7.2 目标架构

```text
官方/RSS/API/社交平台
        ↓
采集适配器 + 定时任务
        ↓
原始内容区（raw_items）
        ↓
标准化 → 去重 → 球队实体匹配 → 事件聚类
        ↓
AI 翻译/摘要/证据信号提取 + 规则引擎
        ↓
信息条目、事件簇、可信度历史（Supabase）
        ↓
平台无关领域服务 + 版本化 API（/api/v1）
        ↓
Web / iOS / Android / 鸿蒙 / 微信小程序
```

当前 MVP 只交付 Next.js Web。业务规则、API 契约、身份映射、通知事件和数据同步从一开始保持平台无关；未来原生端复用后台和契约，不复制 Web 页面内部逻辑。详细边界见 [PLATFORM_ARCHITECTURE.md](./PLATFORM_ARCHITECTURE.md)。

### 7.3 建议核心数据表

| 表 | 用途 |
|---|---|
| `teams` | 球队、联赛、名称、中文名、别名、时区、Logo |
| `team_aliases` | 多语言简称、旧名、常见拼写，用于实体匹配 |
| `sources` | 来源类型、主页、可信等级、是否官方、授权状态 |
| `source_accounts` | 各平台账号与球队/人物的归属及验证状态 |
| `raw_items` | 原始采集结果、哈希、原文、采集状态和错误 |
| `news_items` | 标准化信息、摘要、时间、类型和主来源 |
| `news_teams` | 信息与一个或多个球队的关联及匹配置信度 |
| `event_clusters` | 同一事件的多来源聚合 |
| `cluster_items` | 事件簇与信息条目的关系 |
| `reliability_assessments` | 分数、标签、理由、模型和规则版本 |
| `reliability_history` | 标签变化与审计轨迹 |
| `profiles` | 用户资料和时区 |
| `user_team_follows` | 用户关注球队及排序 |
| `notification_preferences` | 摘要和即时通知偏好 |
| `ingestion_runs` | 每次采集任务的运行状态、数量和错误 |

### 7.4 采集任务设计

- 每个来源使用独立 Adapter，输出统一结构。
- 通过 Vercel Cron 或独立任务队列定时触发。
- 以 `source_item_id + canonical_url + content_hash` 幂等去重。
- 保存原始响应必要字段，便于追溯，但按平台条款控制缓存内容和期限。
- 单一来源失败时隔离重试，不阻塞其他来源。
- 对 API 限额、成本和失败率建立监控。

### 7.5 AI 处理边界

AI 适合：翻译、摘要、球队/人物实体识别、内容类型分类、声明抽取、相似事件聚类、证据信号整理。

规则引擎负责：官方账号硬匹配、标签硬条件、来源黑白名单、冲突规则、展示阈值和敏感内容门槛。最终标签由“规则 + AI 信号 + 人工覆盖”共同产生。

## 8. 项目阶段与里程碑

以下估算以 1 名全栈开发为主、产品经理/运营兼职参与为基准；多人并行时可缩短。

| 阶段 | 预计周期 | 主要交付物 | 验收结果 |
|---|---:|---|---|
| M0 产品定稿 | 1 周 | PRD、原型、首批球队与来源清单、标签规则 | 范围和规则获得确认 |
| M1 用户与日历 | 2 周 | 球队目录、关注功能、日历/日程视图、筛选 | 用户能选择球队并按天浏览现有数据 |
| M2 自动采集 | 2 周 | 官方/RSS 适配器、定时任务、标准化、去重、日志 | 14 支球队连续 7 天自动更新 |
| M3 AI 与可信度 | 2 周 | 翻译摘要、实体匹配、事件聚类、可信度标签及解释 | 抽样准确率达到验收阈值，标签可追溯 |
| M4 后台与封闭测试 | 1–2 周 | 来源管理、人工复核、审计、监控、反馈入口 | 50–100 名种子用户完成两周测试 |
| M5 公测优化 | 持续 | 通知、更多来源、性能和数据质量优化 | 核心指标达到公测目标 |

建议 MVP 总周期：8–10 周。

## 10. 验收标准

### 10.1 产品验收

- 新用户能在 60 秒内选择至少一支球队并看到专属内容。
- 日历能够按日期、球队和可信度正确筛选。
- 每条内容都能查看原始来源和发布时间。
- 绿色内容 100% 可追溯到已验证官方来源。
- 红色内容必须展示至少一个低可信原因。
- 同一事件的重复报道能够聚合，且不丢失来源列表。
- 标签变化后，用户可查看变化时间和理由。

### 10.2 数据与 AI 验收

- 球队实体匹配 precision ≥ 95%，recall ≥ 90%。
- 官方来源识别 precision = 100%（宁可漏标，不可误标绿色）。
- 去重/事件聚类 precision ≥ 90%。
- 中文摘要事实忠实率 ≥ 95%，不得引入原文不存在的关键事实。
- 随机抽样中，可信度标签与人工标注一致率 ≥ 85%。
- 所有低于阈值或敏感类别进入人工复核队列。

### 10.3 运行验收

- 核心来源连续运行 7 天，任务成功率 ≥ 99%。
- 重复执行同一采集任务不产生重复记录。
- 来源失效、API 配额不足和 AI 处理失败均有告警。
- Vercel 生产构建、数据库 migration、RLS 和回滚流程通过演练。

## 11. 核心指标

### 北极星指标

每周有内容消费行为的关注球队数（Weekly Active Followed Teams）。

### 辅助指标

- 首次球队选择完成率。
- 次日/7 日留存率。
- 每用户关注球队数。
- 日历周活跃用户和详情打开率。
- 原文点击率与每日摘要打开率。
- 官方消息采集延迟。
- 重复内容率、错误球队匹配率、标签纠错率。
- 来源任务成功率与每千条信息的采集/API/AI 成本。

## 12. 风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 社交平台 API 费用或政策变化 | 数据覆盖和成本失控 | 官方/RSS 优先；平台 Adapter 解耦；设置月度成本上限 |
| 未授权抓取或全文转载 | 法律与封禁风险 | 使用官方 API/RSS；只存必要元数据和短摘要；保留删除机制 |
| AI 错把传闻标成官方 | 严重损害信任 | 绿色标签采用官方白名单硬规则，AI 无权单独升级为绿色 |
| 来源冒充或账号被盗 | 错误传播 | 官方账号人工验证；异常发布检测；支持快速降级和撤回 |
| 同一消息大量转载造成“多方证实”假象 | 评分虚高 | 做引用链和来源独立性分析，不以文章数量直接加分 |
| 中文翻译或摘要改变语义 | 误导用户 | 保留原文；关键实体/数字校验；抽样人工评测 |
| 数据量和定时任务增长 | 性能/费用问题 | 增量拉取、缓存、批处理、索引、限流和成本监控 |
| 颜色导致可访问性或误解 | 用户误判 | 颜色 + 图标 + 文字；详情展示证据和免责声明 |

## 13. 数据接入约束说明

- X 的 Recent Search 可查询最近 7 天的公开内容；完整历史搜索属于付费或企业能力，当前文档显示 API 采用按量付费，因此 MVP 只应接入精选账号并设置预算上限。
- YouTube Data API 需要 Google Cloud 项目和 API 凭证，并受配额控制；应优先读取已知官方频道的活动或视频列表，避免高成本泛搜索。
- Reddit 等社区平台对 API 使用、内容保留、商业用途和 AI 使用有明确限制；如接入，只用于合规展示和证据分析，不将平台内容用于训练模型，并实现删除同步。
- 其他平台只有在确认开放接口、授权范围、缓存期限和展示规则后才能进入自动采集范围。

## 15. 下一迭代建议

下一迭代只做一个可验证闭环：

> 用户选择 1–5 支球队 → 系统从已授权官方/RSS/API 自动收集信息 → AI 生成中文摘要 → 在日历中按绿色/蓝色展示 → 用户能查看原文与判定依据。

本迭代暂不接入低可信社区来源和红色传闻。真实来源授权完成前使用模拟 Feed 与人工链接开发，不以绕过条款的 HTML 抓取替代。先用高质量来源验证“球队关注 + 日历 + 信息处理 + 可追溯”的产品价值，再扩大社交平台覆盖和可信度复杂度。
